# input

A native macOS voice-input tool. Press Fn once to start recording, press it again to stop, and the text is written where the cursor is at that moment. It uses your own API key (OpenAI, Groq, SiliconFlow, or any service with an OpenAI-compatible API). SwiftUI + AppKit, no third-party runtime dependencies.

input is an independent implementation. It is not the official Typeless client and does not copy all of its features. It covers dictation, translation and voice-driven rewriting of selected text; it does not answer questions, operate the computer or sync history to a cloud.

The interface is in English and Simplified Chinese (Settings → General → Language; "Follow macOS" picks Chinese when the first preferred language of macOS is Chinese).

## Build and run

Requires macOS 14+ and the Swift 6 toolchain. The Command Line Tools are enough; a full Xcode is not needed.

```sh
bash build.sh --install
open /Applications/input.app
```

The app was first called Qingyan. The app name, menu bar item, process and install path are now input; the bundle ID (`local.hopo.qingyan`), preferences, keychain items, history folder and Swift target names keep the old name, so existing permissions, API keys and history carry over. `--install` removes an old `/Applications/Qingyan.app`.

Quit input before installing. `build.sh` signs with the identity in `SIGNING_IDENTITY` and never falls back to an ad-hoc signature. `--install` copies the app to `/Applications/input.app` and registers it; without arguments the app is only built into `build/`. `INPUT_BUILD` sets the build number (the version becomes `0.1.<build>`).

macOS ties permissions (Accessibility, Microphone, Keychain) to the app's signing identity. As long as every build is signed with the same certificate and bundle ID, a new build keeps the permissions of the old one. Do not use a weak designated requirement that matches only the bundle ID to work around this, and do not edit the TCC database.

## First use

1. Open Settings (the gear at the right end of the panel's title row, or ⌘,). The services and keys are at the top: choose the service for recognition and the one for polishing, enter each one's API key, click Save, then Verify. Each service's key is stored separately, only in the macOS keychain, never in project files, logs, history or UserDefaults. A ChatGPT subscription does not include API credit.
2. The top of the panel lists the steps still missing; turn on the Microphone and Accessibility permissions there. The installed app adds itself to the permission lists. `open /Applications/input.app --args --setup-permissions` runs the first-time permission flow: Microphone first, then Accessibility. The system's confirmations must be given by the user.
3. Press Fn / 🌐 anywhere to start. Pauses do not stop the recording; press again to stop. The text is written at the current cursor when it is ready; with no text field it is still saved to History. The microphone button at the top of the panel and "Start recording" in the menu bar item's right-click menu do the same. Esc cancels and deletes the recording.
4. Microphone: the Microphone block on the panel and "Audio and shortcut" in Settings list the input devices that are connected. The one you click is locked (by the device's lasting UID, not its name) and is the only one input records from (2026-11-18 decision: a microphone once picked stays bound). When the locked device is absent, input does not switch to the system default or the built-in microphone; it records nothing. The moment it disconnects (while not recording) the status capsule and the panel say so; if it disconnects during a recording, the recording stops and what was recorded stays in History; after that, Fn only shows the notice. The panel's title reads "Device offline" and the Microphone block opens, so you can reconnect the device or click another one to lock it instead. "System default" removes the lock and follows the system's current input device.
5. Settings → "Audio and shortcut" shows whether Fn has been taken over. With Fn selected and the key monitor running, input sets the system's "Press 🌐 key to" action to "Do Nothing" for the time being, so Fn does not switch input sources, open the emoji picker or start the system's dictation on a double press. If a permission is missing, click "Allow and take over Fn"; the system action is never disabled while the monitor is not running. Do not let another voice tool listen to Fn at the same time.

Click the waveform + input item in the menu bar to open the panel; this also brings it back after it was hidden, closed or minimized. The panel is a narrow vertical glass window, 280 pt wide, that shows the desktop behind it with no opaque background, light or dark with the system appearance. Its width is fixed and its height follows the content: when a block opens, the panel grows to show it in full (up to the screen's height); when Multiple Macs is folded or the Shelf is cleared, it gets shorter. You can also drag the top or bottom edge to make it shorter, and the content then scrolls inside; that only lasts until the next block opens, when the panel grows to fit again. Its position is kept. From top to bottom: the title row (with the History and Settings buttons at its right end); the record button; the input mode (Dictate / Translate / Rewrite, with one fixed line for the mode's options below, so nothing else moves when the mode changes); the microphone; Multiple Macs, with whether each Mac is online (Manage opens it; the arrow at the left of its title folds the block to its title line); and the Shelf at the bottom. While a permission, a key or the shortcut is missing, a setup card appears on the panel. The panel is the whole app: there is no separate settings window and no pop-up dialog (2026-11-14 decision: settings get no window of their own).

History and Settings share a drawer beside the panel. The History button or the gear (or ⌘,, or "Settings…" in the menu bar menu) slides the window out sideways by 316 pt to show the full History (search, clear, and per record: expand, retry, copy, delete) or Settings (recognition and polishing, each service's API key, audio and shortcut, the personal dictionary, general). Switching between History and Settings crossfades inside the drawer; the same button again, or the × at the drawer's top right, slides it back. Every piece of text in the panel and the drawer (results, history records, notices, this Mac's name, Tailscale addresses, pairing codes, dictionary words) is copied with a click on the text itself. The drawer opens to the right, or to the left when there is room only on that side; either way the panel's column stays where it is on screen. The drawer is as tall as the panel and scrolls inside.

When the panel's content scrolls, on macOS 26 and later what scrolls up passes under the title row with a light progressive blur from the system, so the title and status never overlap it; earlier systems have no blur and the content ends at the title row's lower edge. While recording and processing, a small capsule just below the menu bar at the top of the screen shows the state, at less than a tenth of the area of the old bar at the bottom of the screen. While you speak it lights up green and breathes with the volume, so it can be found out of the corner of an eye; it moves along the top edge only when the input focus or input's own panel is right under it, and can be dragged by hand. Most of the panel does not animate (2026-11-14 decision: a height that changes frame by frame with the window resizing behind it stutters and looks poor): opening, closing, switching modes and showing a result happen in one step, content and window alike. The exceptions are details opened by hand (2026-11-18 decision: opening a paired Mac should move smoothly): a Mac's address, permissions and test in Multiple Macs, Manage, and the device list of the Microphone block open and close smoothly. Unlike what was removed on 2026-11-14, where the content and the window each moved on their own clock and the window's edge lagged behind, only the content moves now; the window takes the content's current height on every frame (rounded to the pixel) with no animation of its own, so the two stay together, and its position is saved and the capsule moved only once it settles. The other remaining movements are small and cheap: the highlight of segmented choices, the drawer sliding out beside the panel, a ring spreading from the record button while recording, buttons shrinking slightly when pressed, and the capsule fading in and out. With Reduce Motion on, these switch at once too. Right-click (or Control-click) opens a menu to switch between Dictate / Translate / Rewrite, stop recording, cancel, copy the last result and quit. Closing the panel does not quit the app. The panel is an ordinary window on the desktop (Space) where it was opened and stays there: "Show panel" from the menu bar item on another desktop or in a full-screen app switches to the panel's desktop instead of moving the panel (only when the system is set not to switch desktops when switching apps, and the panel therefore cannot appear, is it brought to the current desktop). When the app starts again (after an update, at login or by hand), the panel comes back only if it was open when the app last stopped, and it does not take keyboard focus. Opening input again from Applications also shows the window.

Quitting input, revoking Accessibility or switching to Control + Option + Space restores the original Fn action; an action you chose meanwhile in System Settings is not overwritten. After a crash, the next launch reads the saved original and restores it; until then it can be changed back in the system's keyboard settings. Fn + arrow keys, Fn + Delete and Fn + F-keys stay key combinations and do not start a recording; the F1–F12 setting is not changed.

To update the system's Fn setting at once, input calls HIToolbox's private `TISGetFnUsageType` / `TISUpdateFnUsageType` at run time; no system file is modified. This is not allowed in the Mac App Store, and a future macOS may remove it. When it is unavailable the panel says so, and "Do Nothing" has to be chosen by hand in the keyboard settings; input does not claim to have taken over Fn.

## Shelf: a clipboard shared by several Macs

The Shelf is at the bottom of the panel. Drop files, images or text anywhere on the panel and they stay there; Paste puts what is on the system clipboard there.

- Use: click an item to put it on the system clipboard (an image goes both as a file and as pixels, a file as a file) and paste it elsewhere, or drag it straight into another app or the Finder. On hover, the × at the top right removes it; the right-click menu has Copy, Show in Finder and Remove.
- Sharing: the Shelf follows the pairings in Multiple Macs; there is nothing else to set up. Each Mac keeps one connection to every Mac in its list, and whatever one of them adds or removes changes on all of them; two Macs that are not paired with each other but both connect to the same third Mac stay in step through it. The title shows how many Macs it is shared with. With Multiple Macs off, the Shelf is local.
- Offline: a Mac that is offline keeps using its Shelf and catches up when it is back; an item removed elsewhere meanwhile is not brought back by it.
- Large files (over 8 MB, such as videos) are not sent to the other Macs when added. The others get a card of a few dozen KB: the file's name, size, origin and a thumbnail (a frame of a video, a page of a PDF), with a down arrow and the size. Clicking (or starting to drag) it on a Mac fetches the file from a Mac that has it, with the progress on the card; another click stops. A file fetched by a click goes to the clipboard when it arrives; a drag waits for the fetch to finish.
- Where a file is fetched from: any online Mac that has it, including one that fetched it before. When two Macs are not paired directly but both connect to the same Mac, that Mac fetches it first and passes it on (one hop at most). When no Mac with the file is online, the card shows an offline icon; it can be fetched once one is back.
- Resume: when a transfer stops (network loss, a stop, quitting input), the part already received is kept, and the next click continues from there.
- Space: the Mac that added a file keeps an APFS clone of it, which takes no extra space on the same volume; moving or deleting the original later does not affect the Shelf. When the copies fetched on another Mac exceed 5 GB, the least recently used are released (the card stays and can be fetched again); "Release local copy" in the right-click menu does it by hand. The adding Mac's own copy is never released automatically.
- Transport: small items travel as text inside messages; large files as raw chunks over the same connection, taking turns with cards, removals and other messages, so other items keep syncing during a large transfer. The speed depends on the route between the two Macs; through a Tailscale relay it is slower than direct.
- Limits: 40 items, the oldest giving way; no limit on file size; images and text from the clipboard up to 64 MB; folders are not supported yet (compress one into a file first).
- Storage and transfer: files are kept in `~/Library/Application Support/Qingyan/Shelf` (folder mode 0700), unencrypted on disk, not uploaded to any cloud or model service. They travel only between Macs in the trust list that are allowed to share the Shelf, on the same port and the same encrypted connection as text.
- Diagnostics: create `shelf-probe.trigger` in `~/Library/Application Support/Qingyan/`; input reads and deletes it within two seconds. `big 20` adds a generated 20 MB file, removed after two minutes; `fetch` fetches every large file not on this Mac; any other text adds an item "input sync self-test", removed after 8 seconds. This lets you check another Mac's Shelf from a terminal.

## Editing existing text by voice

In Dictate mode with Polish on, you can speak an editing command without selecting anything: put the cursor in a text field and say, for example, "clear everything", "delete the previous sentence and replace it with Thursday at three", "change Wednesday to Thursday", "no, let me start over…".

- It takes two steps. The first is the same request as the usual polishing, with one more question: could this be an editing command? Only the transcript is sent in this step. If the model says no, the text is written as usual, exactly as before.
- Only when it could be a command is there a second step: input reads the text in the current field (split at the cursor into the part before and the part after) and sends it with what you said to the text model. The model either decides it is ordinary content after all (you may be dictating an instruction for a colleague or an AI assistant) and it is written as usual, or returns the complete new content of the field.
- Only the part that changed is written back: input compares the old and new text, drops the common beginning and end, selects the different middle through Accessibility and pastes over it. Unchanged text is not touched; clearing selects everything and deletes it. The field is read again just before writing, and if it changed since it was sent to the model, nothing is changed.
- When the field cannot be read (terminals, password fields, custom-drawn fields that expose no Accessibility text, documents over 6000 characters), input falls back to editing only the previous dictation: the text the last dictation wrote, within 10 minutes and with focus in the same window. If no key was typed and no click made since that text was written, it deletes the same number of characters backwards and pastes (this also works in a terminal); otherwise it deletes nothing. With no previous dictation either, what you said is written as ordinary content, and the capsule says the field could not be read.
- Each Mac's status in Multiple Macs: it counts as connected when this Mac can reach it, or when it called in and holds its connection (the long-lived connection that shares the Shelf). When it can reach this Mac but this Mac cannot reach it, the status reads "One-way connection" in orange, with a line saying what works and what does not, rather than "Online" (2026-11-14 decision: say so plainly when a connection is one-way). A Mac behind a router that allows only outgoing connections (its own Tailscale off, reaching the tailnet through the router) cannot be reached by the others but can reach them: its text is written on the other side as usual, the Shelf syncs both ways and the other side shows it online; only writing text from the other side to it does not work.
- When text goes to another Mac, that Mac reads its field and sends the content back to the Mac you speak to, and it is that Mac that applies the edit; only a sender that has completed the handshake (the knock session) can read it.
- Privacy: the field's text is sent to the polishing service only when what you said could be an editing command; ordinary dictation neither reads nor uploads it. With Polish off there are no such steps and no editing by voice.
- The two kinds of misjudgment: a command taken as content is written into the field (delete it and say it again); content taken as a command changes the field (undo with ⌘Z in that app). When unsure, the second step leans towards ordinary content.
- History records what you said, not the edited text.

## Multiple Macs: speak on one, and the text appears on the Mac you are controlling remotely

Install the same input on each Mac. Under Multiple Macs on the panel, turn on working with other Macs, then pair:

1. Click Manage. input asks this Mac's Tailscale for the list of online devices and asks each one who it is; those running input appear under "input on your tailnet". Without Tailscale there is no list, and an address can be entered by hand.
2. Click Pair. The other Mac's panel shows "xxx wants to pair with this Mac", both show the same six-digit code, and clicking Allow there adds each Mac to the other's trust list.
3. From then on press Fn on either Mac as usual. Where the text goes is not chosen by hand: a knock decides (see below).

**Identity and encryption**

- Each Mac generates a key pair on first launch and keeps it in the login keychain. The public key is the Mac's identity; its name and address are only labels.
- Every connection starts with a handshake: each side shows its identity key and a one-time key, and the session key is derived from three key agreements (one-time with one-time, and each identity with the other's one-time key). Only the two Macs holding the two identity private keys can read and write what follows, and recorded traffic cannot be decrypted later even if an identity key leaks. After the handshake every frame is encrypted and numbered; a frame that is altered, replayed, lost or reordered ends the connection.
- So whether a connection can be trusted no longer depends on the network: directly, through a router or on a LAN, no hop in between can see the content.
- Each Mac in the trust list has three permissions of its own: whether it may write text at this Mac's cursor, whether it shares the Shelf, and whether it may read and change this Mac's field when editing by voice. A removed Mac can no longer connect.
- An address change needs no new pairing: click Find, or wait for the other Mac to call in, and the address in the list is updated. A different Mac at a known address is noticed, and text is not sent to it.
- "Only accept connections through Tailscale" is on by default: only connections from Tailscale addresses, or arriving on the Tailscale interface (which includes traffic forwarded with its original address by a router on the tailnet), are answered. With it off, Macs on the same LAN can connect too, and still only from the trust list.
- Two Macs paired with a pairing code before the update do not need to pair again: on first launch of the new version, the former sender asks the former receiver for trust with the old code, the receiver checks it and accepts, and the code is retired.

**The knock**

- When a recording stops, the Mac you spoke to connects to every Mac in its trust list and types a knock into the current window. The knock uses only right-hand modifier keys (holding Option, six presses of Shift or Control) and produces no characters; the combination of six is chosen at random for each recording.
- If the current window is a remote desktop (Screen Sharing, Jump Desktop or another tool), it forwards the knock like any other keys to the Mac you are controlling. input on that Mac recognizes the knock in its key monitor and answers "it's me". The text goes only to it and is pasted at its cursor; both Macs keep a copy in History. The others only saw a handshake and get no text.
- When no Mac answers, the current window is an app on the Mac you spoke to, and the text is written at its cursor as usual.
- All this happens while the recording is being transcribed and adds no waiting. If keyboard focus is still in the same window when the text is ready, the answer is used as is; if you moved to another window meanwhile, the knock is typed again, which adds less than a second at most.
- Several remote windows at once are fine: the knock reaches only the one with keyboard focus.
- When the current window is Screen Sharing or Jump Desktop but no Mac answers (input not running there, the Mac not set to receive or not in the list, or the remote tool did not forward these keys), the text is not pasted into the remote window; it stays in History with the reason.
- Macs in the list that cannot be reached are skipped; a handshake waits 1.5 seconds at most.
- Known limit: the knock also reaches the frontmost app on the Mac you spoke to. The keys are modifiers pressed while Option is held, not double presses of any single key, so they rarely trigger shortcuts; an app that binds such a combination to an action will run it.
- Diagnostics: create `knock-locate.trigger` in `~/Library/Application Support/Qingyan/` (it may contain the interval between key presses in milliseconds); within two seconds input knocks on the current window without sending text and appends the result (handshake time, who answered, how long it waited) to `knock-locate.log` in the same folder.

- When sending fails (input not running there, this Mac no longer trusted, no network), the text is not pasted on this Mac instead; it stays in History on the Mac you spoke to, and the capsule says why. Connecting and answering wait 8 seconds at most.
- When the receiving Mac has nowhere to write (a password field, Secure Keyboard Entry, no Accessibility permission), the text is still saved to its History, and the reason is reported to the Mac you spoke to.
- A Mac lets only Macs in its trust list that are allowed to write text write at its cursor; any other connection is refused after the handshake.
- Recordings transcribed later, after the network returns, go only to History and are not sent to another Mac, as they are not written to this Mac's field either.
- In Rewrite mode, the selected text is read on the Mac you spoke to, and the result goes to the receiving Mac's cursor.
- When the receiving Mac is recording itself, received text is still pasted and saved to History without interrupting its own capsule.

## Releases and updates

- Builds: every push to `main` is checked (`swift run QingyanChecks`), built, signed and published by GitHub Actions (`.github/workflows/release.yml`) as assets of this repository's standing release `builds`: `input-0.1.<build>.zip` (the ten newest are kept) and a `latest.json` naming the newest. The build number only grows.
- Signing: a self-signed certificate, "input signing (SUB&SUB)", valid to 2036. Its private key is the repository secret `INPUT_SIGNING_P12` (with `INPUT_SIGNING_P12_PASSWORD`); a run without it (a fork) builds to check the code and publishes nothing. The certificate is not issued by Apple and does not pass Gatekeeper, so these builds are for Macs that already run input; public distribution would need a Developer ID certificate and notarization. Every build must be signed with the same certificate: macOS ties the app's permissions (Accessibility, Microphone, Keychain) to the signing identity, and a different certificate would make every Mac grant them again.
- Provenance: every published zip has a build provenance attestation signed by GitHub, which names the workflow run and the commit it was built from. To check a downloaded zip: `gh attestation verify input-0.1.<build>.zip --repo subnsub-tools/subnsub-put`. It proves where the zip was built, not that the code is safe; that is what the source here is for.
- Update feed: `https://dashboard.subnsub.com/api/input/latest.json` names the current build (version, file name, size, SHA-256) and `https://dashboard.subnsub.com/api/input/input-<version>.zip` is the package. No sign-in or token is needed.
- Updating: an input installed in Applications reads `latest.json` every 6 hours (and within a minute of launch). When it names a larger build number, input downloads and unpacks it and checks that the size and SHA-256 match `latest.json`, that the version inside matches, and that **the signing identity is the same as the running app's** (the new bundle must satisfy the running app's own designated requirement). When everything passes, and no recording or delayed transcription is in progress, it replaces `/Applications/input.app` and relaunches. On the first launch of a new version the panel always appears in front of other windows (whether it was open before or not, and also after a manual install) without taking keyboard focus (2026-11-14 decision: after an update the panel shows itself instead of staying hidden in the menu bar); an ordinary relaunch of the same version restores it only if it was open when the app stopped. Settings → General → "Install updates automatically" turns this off, and "Check for updates" next to it checks by hand. The feed being public does not weaken this: a replaced file fails the signature check and installs nowhere, and `latest.json` only names a version, not where to download from.
- Keychain (since 0.1.8): API keys and this Mac's identity key are kept in the login keychain but stored and read through the system's `/usr/bin/security` tool (service `local.hopo.qingyan.vault`), not by the app itself. The keychain grants access by the program that stored an item and tells programs apart by Apple's Team ID; a self-signed certificate has none, so the keychain would recognize only each build's own hash and ask for the login password after every update. Items stored through `security` belong to that system tool, so updates no longer prompt. The cost: other programs running as your user can read them through the same tool without a prompt (about the strength of most command-line tools that store tokens); the content is still encrypted with the login password in the keychain, not a plain file.

## Models and data

- Services: recognition and polishing each use a service of their own, which may differ. Built in are OpenAI, Groq, SiliconFlow, and Custom: any service with an OpenAI-compatible API (enter its endpoint URL, such as `https://example.com/v1`; `http://` is accepted only for IP addresses, this Mac and local host names, for models on your own network). Each service has one key; a custom one may have none. Models are picked from the service's suggestions, or "Other model…" takes a name; Verify asks the service for its model list and checks the key and the chosen model.
- Services other than OpenAI use the generic API: after you finish speaking, the whole recording is uploaded as WAV to `/audio/transcriptions` (120-second timeout), and polishing uses `/chat/completions` (60-second timeout, `max_tokens` 8192). So these services show no text while you speak; the result comes at the end. A recording must fit the service's maximum upload size (audio takes about 2.88 MB a minute; Groq accepts 25 MB, about 8.5 minutes, and SiliconFlow 50 MB). A larger recording is kept and can be retried from History after switching services. The personal dictionary is sent as a short prompt with the recording to Groq and custom services; SiliconFlow's API takes no prompt. A polishing result cut off by the length limit is refused and not written.
- The built-in services' addresses and suggested models are taken from their documentation as of 2026-11 (Groq: `whisper-large-v3-turbo`, `openai/gpt-oss-120b`; SiliconFlow: `FunAudioLLM/SenseVoiceSmall`, `deepseek-ai/DeepSeek-V4-Flash`) and **have not been verified with real keys**; when a model is retired, enter the new name with "Other model…". Editing by voice depends on the model following the answer format strictly; with another model, try it yourself.
- The rest of this list is about OpenAI. The default is `gpt-live-transcribe`, 24 kHz mono PCM streamed over a WebSocket while you speak; pressing Fn commits explicitly, and server-side silence detection never ends a recording.
- `gpt-transcribe` is OpenAI's high-accuracy model for recorded speech: after you finish, the whole recording is uploaded as WAV to `/audio/transcriptions`, with the languages to expect (Chinese, English: `languages[]`) and the personal dictionary's words (`keywords[]`). If the API rejects these hints with a 400, the same recording is sent again without them, so the dictation is not lost. A recording may be up to 25 MB (about 8.5 minutes).
- `gpt-4o-mini-transcribe` is offered for compatibility (over the live connection; it may return text only at the end; OpenAI has announced its retirement on 2027-02-26). Model names come from OpenAI's current documentation; check what your own project can use.
- Polish is on by default: after transcription, one `gpt-4.1-mini` Responses API call. It only adds punctuation and paragraphs, removes meaningless fillers (um, uh), stutters and what the speaker explicitly took back, and may fix obvious homophone errors; it does not summarize, shorten, rewrite, reorder, embellish or translate (2026-11-14 decision: the model must not summarize or change the wording). This does not rely on the instructions alone: the result is compared with the raw transcript character by character (ignoring punctuation, white space and case, by longest common subsequence); if more than a fifth of the original characters are dropped (at least 12 allowed) or more than an eighth added (at least 6 allowed), the model's result is not used, the raw transcript is written, and the capsule notes that polishing changed the wording; sentences under 12 characters are not compared. The switch is called Polish, an Off / On choice in two places that are the same setting: the line under the input mode on the panel when Dictate is selected, and above the polishing service in Settings → recognition and polishing. With it off, dictation uses the raw transcript. Translate and Rewrite always need one text-model request.
- The recording is saved on this Mac first, and the network part streams from the same file while recording, so losing the connection does not stop the recording. A recording is 15 minutes at most; the handshake times out after 12 seconds, recognition after 40 seconds from the commit, and the polishing request after 45 seconds. Offline, OpenAI cannot produce text at once, but the recording and the parts already received are kept.
- A recording finished offline goes into a queue for delayed transcription; once online, it is transcribed when the app is idle, updating History only and never pasting into a field activated later. After a network failure input tries once more after about a minute; if that fails, it waits for the next time the network returns or a manual retry, and never retries endlessly. Authentication, model and similar errors need a fix and then a retry from History; a manual retry uses the service and model selected now; a delayed transcription uses the ones selected when it was recorded. When a complete raw transcript exists, only the text step is retried.
- Audio goes straight to the chosen recognition service; polishing and translation send the transcript to the chosen polishing service; only Rewrite sends the selected text. The screen is never read; the current field's text is read and sent only when you said an editing command (see "Editing existing text by voice"). Responses requests set `store: false`; this is not OpenAI's enterprise zero-retention agreement, and the account's data policy still applies on the server.
- The 100 most recent completed texts are kept; pending and failed recordings are not removed by count and can be copied, retried, deleted or cleared in History. They are stored in `~/Library/Application Support/Qingyan/History` (folder 0700, files 0600) as ordinary local files, without extra encryption or cloud sync. PCM audio is 24 kHz / 16-bit / mono, about 2.88 MB a minute. The recording is deleted once transcription and text processing succeed; cancel, delete and clear delete the audio too.
- Sleep, quitting or a crash keep the audio already written to disk, which can be retried later; a buffer not yet written at the very end cannot be guaranteed. In Rewrite mode the selected text is kept with the pending record on this Mac and cleared when done. Without a selection to rewrite, the recording is treated as ordinary dictation.

## Protecting system input

- input does not register an input method and does not replace the current keyboard layout; it uses an event monitor and the Accessibility API in the background.
- Fn together with another key does not start dictation; the panel and the capsule are separate, and the recording capsule never takes keyboard focus.
- Dictate and Translate do not capture the cursor at the start. The current insertion point is read only when the final text is ready; the app, control, value or selection before and after recording are not compared, and the cursor, field or app may change while recording or processing. Rewrite reads the selected text only at the start, and its output also goes to the final cursor. With nowhere to write, the text is saved to History and the original app is not reactivated.
- The selection is replaced through Accessibility where possible; apps that do not support it get Cmd+V. The clipboard is then restored, rich text included, and new content copied meanwhile is not overwritten.
- input never sends Return or clicks a send button. Some terminals may treat line breaks in pasted text as Enter; do not use it to type unchecked multi-line terminal commands.
- Password controls, Secure Keyboard Entry and custom-drawn fields that expose no Accessibility are not written to automatically; recording to History still works. Secure Keyboard Entry may block global shortcuts; recording can be started from the panel. Recording needs the Microphone permission and a writable disk, but no key or network.
- When only the paste keystroke can be sent, there is no proof the target app handled it; the status reads "Paste sent". The time shown runs from the stop key to the write request, not to the target control finishing drawing.

## Local checks

The Command Line Tools have no XCTest, so the checks use Foundation/AppKit directly, assert public behavior and exit with 1 on failure.

```sh
swift run QingyanChecks
```

They cover Fn combinations, repeated triggers, out-of-order transcription events and final results replacing partial ones, request formats, dictionary limits, refusing cut-off responses, error messages that never echo secrets, rich-text clipboard restore on a real isolated pasteboard and protection of new content. The Shelf checks cover storing and restoring text, images and files across restarts, remembering removals, safe file names, the item limit, cards only for large files, releasing fetched copies by last use, and real sync among three Macs: both directions, multi-frame files identical byte for byte, removal, catching up after being offline, relaying through a third Mac, cards only for large files fetched on demand, resuming, fetching one hop away, the notice when the source is offline, and no connection with a wrong code. The voice-editing checks cover the content of the two requests (the first carries only the transcript, the second carries the field's text only as data), splitting the marker, computing the smallest changed span between old and new text (emoji and combining characters included), reading a field on another Mac and writing it back, and that a request without a handshake cannot read the field. The checks of the encrypted channel and trust cover both ends proving their identity, short and long frames round-tripping, forged and replayed frames ending the connection, asking who is there, pairing agreed by both with matching codes, refusal, one-time admission with an old code, another Mac at a known address, the notice to an older version, and per-Mac permissions. The knock checks cover encoding and decoding all 64 combinations, and incomplete, slow and interrupted knocks. The Multiple Macs checks start a real receiver and sender on the loopback address, including that of two receivers only the one that saw the knock answers, the text reaches only that one, and a Mac with a wrong code or no permission gets no handshake: the original text delivered, long text, no paste with a wrong code, no paste for a connection test, the receiver's failure reported back, a malformed connection not affecting later ones, and a timely error when the receiver is not running. Another real Mac and Tailscale are not involved.

The network protocol checks use Python's `websockets` (checked with version 16) and **do not call OpenAI, need no real key and do not record**. Start the mock server, run the checks in another terminal, then stop the server.

```sh
python3 Tests/realtime_fixture.py 18763
swift run QingyanChecks --socket-fixture ws://127.0.0.1:18763
```

They include real URLSession WebSocket traffic, live parts, out-of-order final events, short audio, authentication errors, cancellation and timeouts after stopping. The timeout case takes about 40 seconds. The mock server does not check OpenAI's model availability or recognition quality.

Screenshots of the native UI states (no microphone access, no permission changes):

```sh
swift run Qingyan --render-previews <output folder>
```
